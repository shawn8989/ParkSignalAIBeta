## Parser & OCR interpretation  (12: 9 bugs, 3 improvements)

### [HIGH/bug] No "except"/negation or weekend/weekday/holiday keyword handling — excepted days become the active days (the reported weekend bug)
- **Where:** `test2/Services/ParkingTextParser.swift:103-136 (extractDays) and :86-95 (detectType)`
- **Issue:** extractDays() blindly harvests every day token in the line via `l.contains(key)` with zero awareness of a preceding "except"/"excluding"/"exc." clause, and detectType() reads the restriction type from the same line. I verified empirically: "No Parking 8-9 except SAT SUN" → daysOfWeek=[0,6] (Sat+Sun only) and type=.no_parking, i.e. the app schedules No-Parking on exactly the two days the sign EXEMPTS — precisely the owner's report of an alarm on weekends only. When the exemption is spelled as a keyword the parser doesn't know ("except weekends", "weekdays", "except holidays"), it is silently dropped: "No Parking 8-9 except weekends" → days=[] → defaultDays(.no_parking)=Array(0...6) → restriction applies all 7 days including the exempted weekend. There is no "weekend"/"weekday"/"holiday" vocabulary anywhere in the parser. This propagates to NotificationManager.schedule (repeating weekly alarms on the wrong weekdays) and ParkingSignalEvaluator (RED status on the wrong days).
- **Fix:** Detect a negation boundary ("except", "excluding", "exc", "but not") and split the line: days/keywords AFTER it are the exempt set, subtracted from the active set (active = full applicable set − exempted). Add keyword expansion: "weekend(s)"→[0,6], "weekday(s)"/"mon-fri"→[1..5], "daily/every day"→0...6, and treat "holidays" as a flagged uncertainty rather than a day. When an "except" clause is present but the base set is unstated, default the base to Mon-Fri (typical) rather than all-7, and mark the parse low-confidence for user confirmation.

### [HIGH/bug] Per-line parsing fragments a single stacked sign; a lone "NO PARKING" line becomes all-day/every-day and suppresses the correct whole-text parse
- **Where:** `test2/Services/ParkingTextParser.swift:9-27 (analyze) and :68-79 (path 3)`
- **Issue:** Vision returns one observation per physical text line (VisionOCRService joins them with \n), so a real stacked sign arrives as e.g. "NO PARKING"/"8 AM - 10 AM"/"TUESDAY"/"STREET CLEANING". analyze() loops line-by-line: "NO PARKING" hits path 3 (lines 68-79) → no_parking, days empty → Array(0...6), 00:00-00:00 = No Parking every day, anytime (permanent RED). The "8 AM-10 AM" line has no type → nil; "TUESDAY" → nil; "STREET CLEANING" is street_cleaning but path 3 only fires for no_parking/permit → nil. Because results is now non-empty, the whole-text fallback at :21-24 is skipped — yet feeding the WHOLE blob to restriction(from:) correctly yields street_cleaning, Tue, 08:00-10:00. So the design (prefer per-line, fall back only when empty) makes the wrong fragment win over the correct combined interpretation for the most common sign layout.
- **Fix:** Do not treat each OCR line as an independent rule. Parse the merged block as the primary unit; only split into multiple rules when a line independently carries a type+window (or on strong separators like a blank line / "AND"). Suppress the bare-type "anytime" path (path 3) unless the line also contains "ANYTIME"/"AT ALL TIMES"/"24 H" or is the entire sign. Cross-attach a type-only line ("STREET CLEANING") to a nearby window line.

### [MEDIUM/bug] Empty daysOfWeek is interpreted inconsistently: evaluator treats it as "every day" (RED daily) while NotificationManager treats it as "no days" (never alarms)
- **Where:** `test2/Services/ParkingTextParser.swift:219-228 (defaultDays returns [] for street_cleaning); test2/Utilities/ParkingSignalStatus.swift:118 & :179 (isActive); test2/Services/NotificationManager.swift:46-51`
- **Issue:** defaultDays(.street_cleaning) returns [] with the comment "leave empty so user confirms." But downstream, ParkingSignalEvaluator.isActive uses `if !r.daysOfWeek.isEmpty && !contains(weekday)` — empty days means the guard is skipped, so the restriction is considered active EVERY day within its time window (permanent daily RED). Meanwhile NotificationManager.schedule iterates `for dow in r.daysOfWeek`, so empty days schedules ZERO reminders. Net effect for a street-cleaning sign whose weekday didn't parse: the map shows illegal every day but the user is never alarmed — the worst combination. ParkingEligibilityEvaluator.isActive (:78) has the same empty=all-days semantics.
- **Fix:** Pick one meaning for empty days and enforce it everywhere. Recommended: empty = "unknown, needs confirmation" — evaluator should render it as gray/uncertain (not RED-every-day), and the confirmation UI should force the user to pick days before the restriction can schedule alarms. Never silently expand empty to all-7 in one path and none in another.

### [MEDIUM/bug] Day-range parsing drops interior days when the separator has spaces or is "to" — "MON - FRI" / "MON TO FRI" become [Mon,Fri] only
- **Where:** `test2/Services/ParkingTextParser.swift:112-128 (range) and :138-149 (dayIndex)`
- **Issue:** The range branch builds tokens with `substr.replacingOccurrences(of:"to",with:"-").replacingOccurrences(of:"–",with:"-").split(separator:"-")` and passes them straight to dayIndex without trimming, while dayIndex requires an EXACT match. I confirmed empirically: "MON-FRI" → [1,2,3,4,5] (ok), but "MON - FRI" → tokens ["mon "," fri"] → dayIndex fails → range not built → only the fallback substring scan survives → [1,5]; "MON TO FRI" → [1,5]. OCR very frequently inserts spaces around the dash, and worded ranges are common, so full Mon-Fri windows silently collapse to Monday+Friday — restrictions/alarms simply don't exist for Tue/Wed/Thu.
- **Fix:** Trim each token (`.trimmingCharacters(in:.whitespaces)`) before dayIndex, and make the separator regex tolerant: split on `\s*(?:-|–|—|to|thru|through)\s*`. Add a unit test with spaced and worded ranges ("MON - FRI", "MON TO FRI", "MON THRU FRI").

### [MEDIUM/bug] Leading ordinals hijack the time window, and nth-weekday-of-month is unsupported: "2ND & 4TH TUESDAY 8AM-10AM" parses as 02:00-04:00
- **Where:** `test2/Services/ParkingTextParser.swift:161-198 (extractTimeRange)`
- **Issue:** extractTimeRange takes the FIRST two numeric matches of `(\d{1,2})(?::(\d{2}))?\s*(am|pm)?`. For the very common street-cleaning phrasing "2ND & 4TH TUESDAY 8AM-10AM" the first two numbers are the ordinals 2 and 4, so I confirmed it returns startTime=02:00, endTime=04:00 instead of 08:00-10:00 — a completely wrong window (and completely wrong weeks). The parser also has no representation for "1st/3rd" or "2nd & 4th" week-of-month semantics, so even the correct times would apply on the wrong weeks.
- **Fix:** Strip ordinal tokens (\d+(st|nd|rd|th)) and week-of-month phrases before time extraction, and prefer matches that carry a meridiem or a colon, or that are adjacent to a dash, over bare leading numbers. Add an optional weekOfMonth field to AIRestriction (or at minimum flag "nth-weekday" signs as needs-review) so 2nd/4th-Tuesday cleaning isn't silently mis-scheduled.

### [MEDIUM/bug] 12-hour meridiem inference gaps produce inverted overnight windows: bare "10-6" → 10:00-06:00, "8AM-5" → 08:00-05:00
- **Where:** `test2/Services/ParkingTextParser.swift:182-197 (meridiem inference in extractTimeRange)`
- **Issue:** Meridiem is only inferred for the start from a present end meridiem; when neither side (or only the start) has AM/PM, no correction is made. Confirmed: "10-6" → ("10:00","06:00") and "8AM-5" → ("08:00","05:00"). Because downstream treats end<=start as an overnight window (AnalysisConfirmationView:174, evaluator, DateTimeUtils), a daytime meter window like 10AM-6PM becomes a 20-hour overnight restriction, and 8AM-5PM becomes an overnight 8:00→05:00 window — massively over-restricting and mis-timing alarms.
- **Fix:** When the end lacks a meridiem and end-hour < start-hour with no explicit overnight cue, assume the end is PM (or that both cross noon) so daytime ranges stay same-day. When both sides are bare and 1<=start<end<=12, treat as a daytime window unless an explicit overnight keyword ("overnight", "night", "pm-am") is present. Surface any inferred meridiem as a low-confidence flag.

### [MEDIUM/bug] Duration-only limits are persisted as a daily metered window anchored to scan time (and all-week), turning a one-time max-stay into a permanent daily false restriction
- **Where:** `test2/Views/Scan/AnalysisConfirmationView.swift:163-177; test2/Services/ParkingTextParser.swift:57-64 & :219-228`
- **Issue:** A "2 HOUR PARKING" sign parses to durationMinutes=120, type=.metered, daysOfWeek=defaultDays(.metered)=Array(0...6). saveAndSchedule sets startDate=now, endDate=now+2h and stores a Restriction. But Restriction/evaluator only use the hour:minute-of-day of those Dates (ParkingSignalStatus.isActive), and days are all-7 — so parking at 14:30 today creates a metered window that re-appears as 14:30-16:30 EVERY day forever, showing purple daily regardless of when the user actually parks. A max-stay duration is not a recurring clock window and shouldn't be modeled as one.
- **Fix:** Model duration limits as a one-shot countdown from the actual park/scan moment (a single expiring timer), not as a recurring daily Restriction. Keep durationMinutes distinct from window-based restrictions in the evaluator so a max-stay never contributes a recurring colored window; if you must persist it, store the absolute expiry and clear it when the session ends.

### [MEDIUM/bug] Alarm countdown mis-fires: it keys off the whole-blob OCR text containing "hour"/"minute" and applies to every created restriction
- **Where:** `test2/Views/Scan/AnalysisConfirmationView.swift:186 (ocrText: ocrText) and :207-216 (countdown loop)`
- **Issue:** Each created Restriction is given `ocrText: ocrText` — the ENTIRE scan blob, not the specific line it came from. The countdown loop then schedules an AlarmKit timer for any restriction whose ocrText `.contains("hour") || .contains("minute")`. So on a multi-piece sign where just one line says "2 HR", every restriction (including "No Parking 8AM-10AM" windows) gets a countdown, with seconds = endTime−startTime measured from NOW rather than from the window's real start. Result: spurious countdown alarms unrelated to any actual time limit.
- **Fix:** Store the per-restriction source line in AIRestriction.notes and pass that (not the whole blob) as the Restriction's ocrText. Gate the countdown on `r.durationMinutes != nil` (the structured field) instead of substring-sniffing free text, and derive the countdown from durationMinutes.

### [MEDIUM/bug] Repeating weekly reminders can be orphaned because their identifiers are derived from mutable day/time values
- **Where:** `test2/Services/NotificationManager.swift:66-68 (schedule id) and :82-97 (cancel recomputes id)`
- **Issue:** schedule(for:) creates repeating UNCalendarNotificationTrigger requests with id "restriction.<id>.<weekday1_7>" computed from the restriction's current startTime + daysOfWeek, and cancel(for:) rebuilds the ids the SAME way from the restriction's CURRENT values. If a restriction's days or start time change between scheduling and cancelling (e.g. the user fixes a wrong parse like the weekend bug, or edits the window), the recomputed ids no longer match the ones actually scheduled, so the stale repeating notifications are never removed and keep firing forever. This directly compounds the negation bug: correcting the wrong days does not stop the already-scheduled wrong-day alarms.
- **Fix:** Persist the exact scheduled identifiers (e.g. store the alarm/notification ids on the Restriction or in the AlarmService metadata store) and cancel by the stored ids, not by recomputation. On any edit, cancel-by-stored-id then reschedule.

### [MEDIUM/improvement] No confidence/uncertainty signaling anywhere in the OCR→restriction path; silent defaults are presented as definitive
- **Where:** `test2/Services/VisionOCRService.swift:16-20 (topCandidates(1), confidence discarded); test2/Models/AIAnalysisModels.swift:14-21 (no confidence field); test2/Services/ParkingTextParser.swift (all inference paths)`
- **Issue:** VisionOCRService keeps only topCandidates(1) and throws away VNRecognizedText.confidence and all alternate candidates, so dirty/ambiguous OCR is indistinguishable from a clean read. AIRestriction carries no confidence or "assumption" metadata, and the parser silently applies major inferences — meridiem guessing, all-week defaulting, dropping unrecognized "except" clauses — with no signal. AnalysisConfirmationView then shows every parsed restriction as a confidently-toggled row (defaulted ON, line 89), so a low-quality guess looks identical to a certain read and the user is likely to accept it.
- **Fix:** Propagate Vision confidence out of recognizeText and add a confidence/assumptions field to AIRestriction (e.g. flags: meridiemInferred, daysDefaulted, negationSeen, lowOCRConfidence). In the confirmation UI, visually mark low-confidence/assumed restrictions, default their include-toggle OFF, and require the user to confirm days/times that were inferred rather than read.

### [MEDIUM/improvement] Replace/augment the manual "With/Against Traffic" selector with address-parity side inference; the with/against→left/right mapping is also wrong for one-way streets
- **Where:** `test2/Utilities/DrivingSide.swift:19-40; test2/Services/GeocodingService.swift:36 (subThoroughfare already captured but parity unused)`
- **Issue:** DrivingSide.storedSide maps a manual "with"/"against" choice to a stored "left"/"right" that ParkingSignalEvaluator.scanAppliesToUserSegment uses to gate whether a scan's restrictions apply (ParkingSignalStatus.swift:59-62). This conflates two different concepts: "with/against traffic" is a travel direction, whereas the segment match needs side-of-street. On one-way streets both curbs are "with traffic," so the mapping is ambiguous/incorrect, and the manual toggle is easy to get wrong. GeocodingService already extracts the house number (subThoroughfare) but discards it — US address parity (even vs odd numbers typically fall on opposite sides) can infer which side the user is on automatically. This is the owner's point (1) and is well-founded.
- **Fix:** Use house-number parity from the geocoded address (and the sign's own posted address when OCR captures one) to infer side-of-street, and store side-of-street directly rather than a with/against direction. Keep a manual override for one-way streets and cities with mixed parity, and show the inferred side so the user can correct it. This removes a common source of "restrictions didn't apply to me" errors driven by a mis-set toggle.

### [LOW/improvement] Minor interpretation gaps: "PARKING <window>" degrades to a no-op .other, single-time signs are dropped, and OCR alternates/casing are unused
- **Where:** `test2/Services/ParkingTextParser.swift:31-50 & :86-95; test2/Services/VisionOCRService.swift:23-25; test2/Utilities/OCRTextUtils.swift:29`
- **Issue:** (a) A sign like "PARKING 9AM-6PM" (context word only, no limit) detects type .other and returns an .other restriction that the evaluator and NotificationManager both ignore — a recognized rule that silently does nothing. (b) extractTimeRange requires >=2 time matches, so a single-time street-cleaning sign ("STREET CLEANING 8AM WED") yields nil (path 3 only handles no_parking/permit). (c) VisionOCRService discards all but the top candidate and relies on usesLanguageCorrection, which can "correct" sign tokens (e.g. times) unhelpfully; there is no customWords list of parking vocabulary. (d) OCRTextUtils.mergeAndDeduplicate dedupes by lowercased line, which is fine but does nothing to reassemble multi-piece signs. These are polish-level but each narrows real-world coverage.
- **Fix:** Treat bare "PARKING" with a window as advisory/unknown rather than a silent .other; support single posted-time signs (assume a short default window or flag for confirmation); pass parking-domain customWords to Vision and consider inspecting lower-ranked candidates when the top one fails to parse; and keep the merge step but pair it with block-level (not per-line) parsing.


## Alarms & notification scheduling  (17: 13 bugs, 4 improvements)

### [HIGH/bug] Parser has no "except"/negation handling — schedules alarms on the exact days that are excluded (the "weekend only" bug)
- **Where:** `test2/Services/ParkingTextParser.swift:103-136 (extractDays), 31-82 (restriction)`
- **Issue:** extractDays() scans the whole line for day tokens and inserts every one it finds, with no awareness of "except"/"excluding"/"but not". For a sign like "No Parking 8-9AM Except Sat Sun" the loop at 131-134 matches "sat" and "sun" and returns [6,0] — i.e. it schedules the restriction precisely on the two days it must NOT apply. This is exactly the owner's reported symptom (a weekend-exception sign firing on weekends only). Compounding it: "weekend"/"weekends"/"weekday"/"weekdays" are not tokens at all (dayTokens, 151-159), so "No Parking 8-9 except weekends" finds zero days, then defaultDays(for: .no_parking) at 219-228 returns Array(0...6) — all 7 days. Either phrasing produces wrong scheduling.
- **Fix:** Detect a negation clause ("except", "excluding", "but not", "no [day]") and split the text into applies-to vs excluded segments before token matching; subtract excluded days from the included set (or from the default full week). Add "weekend"/"weekday" as day-set tokens. When a negation is detected but ambiguous, mark the restriction low-confidence and force the user to confirm days rather than silently scheduling.

### [HIGH/bug] "MON THRU FRI" / "MON THROUGH FRI" parses as Mon+Fri only, dropping Tue–Thu
- **Where:** `test2/Services/ParkingTextParser.swift:112`
- **Issue:** The day-range regex only accepts the separators '-', '–', and 'to': (sun|mon|...)\s*(?:-|–|to)\s*(sun|...). The extremely common sign wording "MON THRU FRI" and "MON THROUGH FRI" does not match, so the range branch is skipped and only the individual-mention loop runs, adding just "mon" (1) and "fri" (5). Tuesday/Wednesday/Thursday are silently omitted, so a Mon–Fri restriction only schedules alarms on Monday and Friday.
- **Fix:** Add "thru" and "through" (and "til"/"until") to the range separator alternation, e.g. (?:-|–|to|thru|through). Add a unit test for "MON THRU FRI" → [1,2,3,4,5].

### [HIGH/bug] Deleting or editing a restriction never cancels or reschedules its notifications — stale alarms fire forever
- **Where:** `test2/Views/Spots/ParkingSpotDetailView.swift:1002-1009 (onDelete) & 221-249 (Add/Edit onSave); test2/Services/NotificationManager.swift:82-98`
- **Issue:** NotificationManager.cancel(for:spot:) is never called anywhere in the codebase (verified by grep). restrictionsSection.onDelete deletes the Restriction model but leaves its repeating UNCalendarNotificationTrigger (identifier "restriction.<id>.<weekday>") pending — the user keeps getting reminders for a restriction they removed until the app is reinstalled. The Add/Edit save path (221-249) likewise never (re)schedules or cancels: editing a restriction's time or days leaves the old weekly notification in place (its id is keyed on restriction.id + weekday, so changed days orphan the old weekday entries and the new time never gets a notification unless a scan/city-import re-runs schedule()). Manually added restrictions get no weekly reminder at all.
- **Fix:** On delete: call NotificationManager.shared.cancel(for: [restriction], spot:) before context.delete. On edit/add save: cancel the old identifiers, then re-run schedule(for:spot:). Because cancel recomputes ids from current lead time, cancel using getPendingNotificationRequests filtered by the "restriction.<id>." prefix instead of recomputing weekday (see the lead-time finding).

### [HIGH/bug] "Next restriction" park alerts fire AT the restriction start with no lead time subtracted
- **Where:** `test2/Views/Spots/ParkingSpotDetailView.swift:1106-1133; test2/Models/ParkingSpot+Status.swift:7-20; test2/Views/Cars/CarListView.swift:517-565`
- **Issue:** spot.nextRestrictionDate() returns the restriction START time (no lead). scheduleNextRestrictionNotification uses that date directly for the UNCalendarNotificationTrigger (comps from `next`, 1116-1117) and for the AlarmKit countdown (seconds = next.timeIntervalSinceNow, 1129). So the "Move your car — restriction starts soon" alert actually fires exactly when the restriction begins, i.e. when the car is already illegal — defeating the entire lead-time premise. This contradicts NotificationManager.schedule(), which does subtract leadMinutes (computeLead), so the two scheduling paths behave inconsistently. CarListView (517-565) has the identical defect.
- **Fix:** Subtract the user's lead time before scheduling the park alert: fire at next.addingTimeInterval(-Double(leadMinutes)*60) (guarding against a past date). Centralize both the weekly and the one-shot park path through one helper so lead handling can't drift.

### [HIGH/bug] CarListView alert cancellation uses the wrong identifier and never cancels anything
- **Where:** `test2/Views/Cars/CarListView.swift:565 vs 520`
- **Issue:** Alerts are scheduled with id "nextRestriction.car.<carUUID>.spot.<spotUUID>" (line 520) but cancelNextRestrictionNotification removes id "nextRestriction.car.<carUUID>" (line 565) — no ".spot.<uuid>" suffix. removePendingNotificationRequests(withIdentifiers:) requires an exact match, so this call is a no-op: alerts scheduled from the Cars screen can never be cancelled, and the paired AlarmKit countdown isn't touched either. (ParkingSpotDetailView.cancelAlert at :1135-1141 correctly uses hasPrefix filtering — the two screens diverge.)
- **Fix:** Match by prefix like ParkingSpotDetailView: fetch pending requests and remove those whose identifier hasPrefix "nextRestriction.car.<carUUID>.spot."; also cancel the associated AlarmKit alarm via the car/spot metadata stored in AlarmService.

### [MEDIUM/bug] Overnight restriction windows are not "active" after midnight — wrong signal and missed/false alerts
- **Where:** `test2/Utilities/ParkingSignalStatus.swift:116-127 & 178-188; test2/Models/ParkingSpot+Status.swift:24-42`
- **Issue:** isActive() only evaluates the window built for TODAY'S weekday. For an overnight restriction such as Sat 22:00–06:00 (daysOfWeek=[6]), at Sunday 02:00 the current weekday is Sun(0), which is not in [6], so isActive returns false and the curb signal shows green/gray even though the car is inside the Saturday-night window that runs into Sunday morning. The code adds 24h to `end` when end<=start, but never checks whether a window that STARTED on the previous day is still running now. Affects the RED signal, computeCannotParkNow, and yellow lead detection.
- **Fix:** Also test the previous day's window: for each restriction, if yesterday's weekday is in daysOfWeek, build start=yesterday@startTime, end=start rolled to endTime (+24h if overnight), and check now within it. Apply the same fix in ParkingSpot.isRestrictedNow and the AIAnalysisResponse evaluator.

### [MEDIUM/bug] Every park alert schedules two alarms (calendar + AlarmKit), and re-scheduling piles up uncancellable AlarmKit alarms
- **Where:** `test2/Views/Spots/ParkingSpotDetailView.swift:1106-1141; test2/Services/AlarmService.swift:134-177,260-269`
- **Issue:** scheduleNextRestrictionNotification always schedules BOTH a UNCalendarNotificationTrigger and an AlarmKit countdown for the same event. On iOS 26 (AlarmKit compiled in via ALARMKIT_HAS_STANDARD_BUTTONS, confirmed set for the app target) the user gets two alerts; pre-iOS 26 the countdown falls back to yet another local notification. Worse, the calendar path dedups by removing its fixed id first (1110), but each AlarmKit countdown gets a fresh random UUID (AlarmService.swift:138) and is never deduped or cancelled — tapping "Schedule" repeatedly or re-parking accumulates AlarmKit alarms. cancelAlert (1135-1141) only removes UN requests, so the AlarmKit alarm survives and still fires after the user cancels.
- **Fix:** Pick one delivery mechanism per event (prefer AlarmKit when authorized, else the local-notification fallback) instead of scheduling both. Give the AlarmKit alarm a deterministic id derived from car+spot (or look it up via the stored metadata) so it can be deduped and cancelled; have cancelAlert also cancel the matching AlarmKit alarm.

### [MEDIUM/bug] Empty daysOfWeek is treated as "every day" by the evaluator but "no days" by the scheduler — silent no-alarm
- **Where:** `test2/Services/ParkingTextParser.swift:219-228; test2/Services/NotificationManager.swift:51; test2/Utilities/ParkingSignalStatus.swift:118,179`
- **Issue:** The signal evaluator's isActive treats an empty daysOfWeek as active every day (guard is `!daysOfWeek.isEmpty && !contains`). But the scheduler treats empty days as nothing: NotificationManager.schedule loops `for dow in r.daysOfWeek` (no iterations), and nextIllegalStart/nextRestrictionDate `continue` on empty days. So a restriction with no parsed days displays as a daily RED restriction yet never generates any alarm. Street cleaning is especially exposed: defaultDays(for: .street_cleaning) returns [] (222-224), so a "Street Cleaning 8-10AM" sign whose weekday didn't parse becomes an every-day RED with zero reminders.
- **Fix:** Make the two paths agree. Either forbid empty daysOfWeek (default to all 7 and let the user narrow it, forcing confirmation for street cleaning), or have the evaluator treat empty as "unknown/none" too. At minimum, surface a warning when a saved restriction has empty days so the user knows no alarm will fire.

### [MEDIUM/bug] SwiftData model accessed off the main actor inside the notification completion handler (data race / potential crash)
- **Where:** `test2/Views/Spots/ParkingSpotDetailView.swift:1143-1158`

### [MEDIUM/bug] Re-Analyze / re-scan appends duplicate Restriction objects, doubling scheduled alarms

### [MEDIUM/bug] AlarmKit duration-countdown is gated on raw OCR text containing "hour"/"minute" instead of durationMinutes
- **Where:** `test2/Views/Scan/AnalysisConfirmationView.swift:208-216`
- **Issue:** The decision to schedule an AlarmKit countdown checks `r.ocrText.lowercased().contains("hour") || contains("minute")` rather than the structured durationMinutes value. A "No Parking 24 Hours" or "Tow Away — 7 Minutes" sign will spuriously schedule a countdown timer for a non-time-limited restriction, while a genuine duration restriction whose notes got normalized without those words is missed. ### [MEDIUM/bug] AlarmKit alarm countdown display is wrong — endDate recomputed from now on every refresh
- **Where:** `test2/Services/AlarmService.swift:189-207; test2/Views/Alerts/AlarmListView.swift:29`
- **Issue:** In allAlarms(), an AlarmKit alarm's endDate is computed as Date().addingTimeInterval(pre) where `pre` is the countdownDuration.preAlert (the TOTAL configured duration, not the remaining time).
